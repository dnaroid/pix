# Desktop runtime context and model limits

<!-- markdownlint-disable MD013 -->

## Type

Change

## Lifecycle

Active implemented contract.

## Goal

Bring the TUI's context-usage, prepared DCP context-map, and current-model quota signals into Pix Desktop without copying terminal presentation into the GUI. Desktop keeps durable DCP statistics as a separate protocol capability while rendering the live context state as dense IDE status chrome and a lightweight click-open panel.

## Behavior

- Once an active Desktop session runtime is ready, the status bar shows the current context fill percentage and a slightly extended horizontal capacity track.
- Compact status chrome labels context as `ctx`, omits redundant hourly/weekly and `resets` text (window names and reset meaning remain in hover details), and shows Claude Code provider model names without the `Claude Code ` prefix in the model/thinking display. Provider IDs and routing are unchanged. Context and quota use content-sized flex layout rather than equal grid columns; bounded inline controls clip excess content at very narrow widths instead of painting over neighboring controls, while click-open panels remain unclipped.
- Quota detail breakpoints use the available Context/Usage container width, not the viewport: the `Usage` label appears from 380px, reset countdowns from 480px, and the bounded account label from 600px. Loading placeholders follow the same thresholds. Model controls, activity HUD, and other panes therefore reduce detail only when they actually reduce the telemetry slot's width.
- Context danger thresholds match the TUI on the numeric percentage only: up to 30% is the normal/success range, 31–50% warning, and above 50% error. Desktop renders the normal numeric percentage in neutral light gray instead of success green; warning/error keep their semantic colors. The progress track keeps its existing capacity/DCP category coloring.
- When a prepared DCP context map is available, the occupied portion of the status-bar track remains categorically colored for other/retained content, compression candidates, protected incomplete tool groups, and current summaries; free capacity remains visually separate. Clicking the context control opens a compact non-modal panel with absolute context tokens/current window, an enlarged full-width version of the same capacity track, and a compact color legend with approximate category token volumes. Hovering or keyboard-focusing the control no longer opens that panel. The click panel preserves the status-bar track's unknown/occupied/free semantics and uses the same live context map without loading durable statistics. The live DCP `tokensSaved` estimate is also shown directly in the status bar when available. The saved value is the extension's running estimate of context removed by pruning/compression, not the durable statistics report's measured commit gain and not a billing counter.
- The Context panel replaces the former click-open DCP statistics surface in the status bar. Opening it performs no durable DCP statistics request and exposes no compression action. The underlying DCP statistics request and `/dcp compress` runtime capability remain available to other consumers, but are no longer attached to this status-bar interaction.
- The Context panel uses semantic Desktop popover/chrome tokens, closes on outside pointer interaction or Escape, and does not block the rest of the workbench.
- When the active model/provider exposes account quota data, the status bar shows hourly and/or weekly remaining percentages with compact horizontal tracks and reset countdowns. Weekly tracks are divided into seven equal day slices; their hover text labels those slices from the reported window timing. The provider still supplies one aggregate weekly remaining percentage, so the UI does not invent per-day usage values.
- Anthropic subscription OAuth (`sk-ant-oat…`) retains its five-hour/seven-day quota lookup and takes precedence over response-derived usage. With a regular Anthropic API key (`sk-ant-api…`), Pix instead observes `anthropic-ratelimit-*` headers on actual Messages API responses. It displays the lowest remaining percentage among valid request, input-token, output-token, and token limits as one short-window rate-limit indicator, using that limit's own RFC 3339 reset time and a descriptive rate-limit label rather than presenting it as a five-hour subscription quota. Missing or malformed limits do not create a status; no extra request is made for API-key usage, and this short window does not participate in projected-exhaustion warnings without a known duration.
- Models routed through `pi-claude-code-provider` use Claude Code's own subscription credential for the same five-hour/seven-day quota lookup, independently of Pi's `anthropic` auth classification. Pix reads the current `claudeAiOauth` token from Claude Code's macOS login Keychain service (including the per-directory service for `CLAUDE_CONFIG_DIR`) or its `.credentials.json` fallback only for quota polling; it never refreshes or writes Claude Code credentials or includes tokens in Desktop/ACP status. A Keychain entry that is present but expired, malformed, or not an OAuth token falls through to the `.credentials.json` fallback instead of masking it, because Claude Code refreshes the two copies at different times and either may hold the current login. Expired or absent credentials in both locations yield unavailable quota until Claude Code refreshes them; the last successfully observed quota can remain visible only as explicitly **stale** cache, with each window removed at its own reset (never as a fresh observation). The cache belongs to the Claude Code route and is not copied into a different provider's status; ordinary unavailable quota with a present credential still clears the display. While the Claude Code credential is absent, quota polling retries at a bounded faster cadence (~30–60s) instead of waiting for the five-minute interval: those retries read only the Keychain/credentials file and perform no provider network request, so quota appears within about a minute after Claude Code refreshes its login. The faster cadence is armed only for credential-absent unavailability (Desktop recognizes it through the response's `modelUsageCredentialPending` flag); when a token exists, an empty endpoint response keeps the regular cadence. Pix follows the adapter's restricted Claude child environment, which does not forward Pi's API key or OAuth-token environment variables. This is an opt-in-to-provider, best-effort integration with Claude Code's credential format and Anthropic's undocumented OAuth usage endpoint, not a supported Claude Code quota API.
- Observed rate limits belong to the session and request model that produced the response. Switching models or sessions (including concurrent Desktop runtimes) cannot reuse a previous model/session's response headers. An accepted response updates active usage promptly rather than waiting for five-minute provider polling; closing/replacing a session invalidates its captured limits and stale callbacks.
- Model-limit color thresholds match the TUI on the numeric percentage only: below 20% remaining is error, below 50% remaining is warning, otherwise the normal/success range. Desktop renders that normal numeric percentage in neutral light gray instead of success green; warning/error keep their semantic colors. Quota progress fills remain neutral gray. The TUI long-window projected-exhaustion heuristic is retained and its triangle uses the semantic warning color so the projection is visually recognizable even when the numeric percentage is still in the normal range.
- Clicking `Usage` opens the on-demand session-spend popover defined in [session-usage.md](./session-usage.md); it does not force a provider quota refresh. The popover is a compact `provider → model → tokens · cost` breakdown. Parent-agent, async-subagent, retry, and fallback calls are merged into the model that actually incurred them. Model names use the normal Pix model colors. The popover does not show account quota, provider/session-share percentages, or a separate agent/subagent subtotal. For a ready session whose active route uses `pi-claude-code-provider`, it additionally offers an explicit **Refresh limits** control; drafts and other routes do not show it. Clicking this control launches one bounded, headless Claude CLI login nudge asynchronously, discards its output, then rereads Claude Code's local credential and queries Pix's normal quota endpoint. It does not parse undocumented CLI output into quota, refresh recorded session spend, or block the UI. Duplicate clicks/sessions share at most one Claude child; the button is disabled while that session is refreshing. Failures show a retryable message, preserving cached quota only according to the stale-window rule above.
- Normal model-quota refresh still happens when the active runtime/model changes and every five minutes. The `Usage` control remains available while a prompt or quota refresh is running because reading recorded spend is independent of provider quota I/O. The only exception to the five-minute cadence is the credential-pending Claude Code retry described above, which Desktop schedules per session (runtime and draft) while responses keep flagging a missing local credential; forget/reset and a superseded draft selection cancel it.
- Desktop status chrome does not repeat workspace identity or the current Git branch. Project identity remains available in the titlebar/project switcher, and branch information remains in Source Control. Removing the status-bar identity also removes the dedicated 30-second branch-only polling path; Git state continues to refresh through Source Control and the existing sidebar indicator mechanisms.
- While Desktop is starting, a session tab is switching through history/runtime activation, or the first runtime-status snapshot has not arrived, the status bar keeps its normal Model/Context/Usage footprint with non-interactive skeleton placeholders for values that are not known yet. Values that are already available remain real; connection error/stopped states are never hidden behind loading placeholders.
- A UI-only New Conversation draft has no runtime context/DCP state, so its status bar keeps a non-interactive Context skeleton in that slot instead of inventing telemetry. The Model slot becomes real as soon as draft configuration is available, and quota windows replace the Usage skeleton when the staged model/thinking provider exposes usage data.
- Draft quota is loaded through the existing sessionless draft-config path and never allocates an ACP/Pi session. Changing the staged model or thinking level invalidates the previous draft quota and starts a best-effort refresh for the new route. Opening Usage on a draft does not create a session or force another quota request.
- An open draft with an explicit model refreshes quota every five minutes, including after a failed initial lookup, and preserves already displayed quota on transient failures. Credential-pending responses use the faster retry cadence instead. Restaging cancels the old timer, selecting Auto invalidates in-flight quota replies, and closing/resetting a draft stops its polling.
- Antigravity quota refresh is also keyed by the active thinking level because legacy per-model fallback can route current versioned Gemini Flash models to tier-specific Google model keys (for example `gemini-3.8-flash-high` for `xhigh`). Changing thinking therefore refreshes quota immediately instead of waiting for the periodic poll.
- Antigravity live quota lookup now prefers `retrieveUserQuotaSummary` on the current native agy transport (`daily-cloudcode-pa.googleapis.com` then prod, agy CLI 1.1.24 User-Agent, gzip). The explicit Google `5h` and `weekly` buckets are mapped directly to status-bar windows instead of inferring a window type from time remaining until reset.
- For multi-account Antigravity auth, the `Σ` status is the mean remaining quota across every account that returned the same explicit window; its countdown uses the nearest reset in that pool. This keeps account rotation capacity visible instead of reporting only the currently active account.
- A rejected saved Antigravity access token is refreshed through the configured/stored Google OAuth client and retried. If the summary API is unavailable, the lookup falls back to native-header `fetchAvailableModels`, then to provider-observed cached quota; current versioned Flash models may use the shared cached `gemini-flash` bucket when an exact route is absent.
- Antigravity quota lookup uses the configured Pi agent directory (`getAgentDir()` / `PI_CODING_AGENT_DIR`) and `PI_ANTIGRAVITY_GOOGLE_CLIENT_*` environment credentials in addition to OAuth-client metadata already stored with the provider account.
- Context data is primarily event-driven: ACP pushes a lightweight `pix/session-state` `context-usage` snapshot after Pi `message_end` boundaries and after successful compaction. The same sampled Pi session-stats response also pushes `dcp-tokens-saved`, so the inline and click-panel estimate advances on the same trustworthy boundaries without an extra RPC. Streaming deltas do not trigger context/DCP-savings polling, so long tool/model loops update between messages without waiting for the whole prompt to settle. Extension slash commands handled entirely in input preflight get one equivalent boundary snapshot because they may mutate context without emitting agent/message lifecycle events.
- The old post-prompt context-only `runtime_status` request is not needed once push updates are active. Runtime activation still loads an initial status snapshot, and the five-minute quota refresh remains as periodic reconciliation while refreshing model limits.
- After successful compaction ACP immediately pushes Pi's post-compaction context state. When Pi reports context tokens as unknown until the next valid assistant response, Desktop shows that unknown state instead of retaining a stale pre-compaction percentage. Opening the Context panel does not request durable DCP data, so no full-history DCP read is added to the compaction/post-turn hot path.
- A failed quota refresh retains the previously displayed quota snapshot; an explicit unavailable/unsupported result clears it except credential-pending Claude Code unavailability with an unexpired, explicitly stale last-success cache.
- Quota refreshes are tracked with a generation independent of snapshot (context/DCP) refreshes: a concurrent non-quota snapshot refresh must not invalidate a successful in-flight quota refresh; only a newer quota refresh supersedes an in-flight one.
- Concurrent quota refresh requests for the same Desktop session/model/thinking route share one ACP-side provider query. Desktop generation guards still decide which response may update visible state, so deduplication removes redundant network I/O without weakening stale-response protection.
- The manual Claude Code login nudge uses a separate per-session busy/owner guard. Ordinary context snapshots continue while it runs, but an older automatic quota reply cannot overwrite its result; a route/session change during CLI or endpoint lookup invalidates the manual reply. Forget/reset invalidates both completion and busy-state cleanup. The child has a fixed timeout, termination grace and kill escalation, and never captures stdout/stderr.
- DCP and session-usage requests have independent generation guards within a live per-session owner. Forget removes that owner rather than retaining a closed-ID tombstone; reopening creates a distinct owner, so repeated local counters cannot let an old completion update the new runtime. A reset lifecycle generation invalidates status, DCP, and usage responses plus their busy-state cleanup, even when the same session and client are reused. Stale responses cannot recreate missing state.
- Runtime status is scoped per Desktop session and is cleared when that runtime is forgotten or the ACP connection is reset.
- The same status-bar chrome also hosts the separate Session activity HUD only while there is hidden live activity. With the inspector closed, each of the first six active agent icons is its own compact control; hovering or keyboard-focusing an icon shows the same key live details as the inspector (agent/run identity, resolved role when known, status, elapsed time, task/scope, model, latest activity, and retry count), while clicking it opens the inspector. Running and retrying icons pulse gently while planned icons remain still, with reduced-motion preferences disabling the pulse. The agent label renders as `id (role)` when the task preview carries `subagentType`. Additional active agents collapse into a compact `+N` control that opens the inspector. Completed/total Plan progress is a neighboring control whose hover/focus surface shows the full non-deleted Plan in stable hierarchy order, with complete per-item status and available active-form/description/thinking/owner/blocker metadata. That Plan surface also exposes the same `Clear session plan` trash action as the Session inspector; both surfaces share one session-owned pending guard and the same ACP clear request. The Plan list is bounded and scrollable, and each hover/focus opening automatically centers the current item using `in_progress` → `pending` → `deferred` priority. The Subagent surface keeps its fixed identity/status header and model/activity footer around a bounded scrollable task body. Clicking Plan progress also opens the inspector. Empty sessions and an already-open inspector render no Session status control. Session Plan/Subagent state comes from pushed session-state snapshots rather than the runtime-status request, so opening or updating that HUD does not add quota/context polling.
- The Session inspector no longer duplicates DCP telemetry; it contains the Agents and Plan activity sections only. Their independently collapsible native `<details>` accordions preserve the existing first-snapshot/manual-toggle behavior.
- The compact status-bar context track is the always-visible DCP capacity visualization. Total occupied/free capacity comes only from the already-held live SDK `tokens` and positive `contextWindow` denominator; the separately reported percentage is not a denominator. Invalid or unknown context produces neutral unknown capacity rather than invented free space, and over-capacity samples fill the bounded track while retaining their actual textual percentage.
- Within occupied capacity, DCP category volumes are explicitly **approximate**, from a dated **last prepared DCP projection** carrying a runtime revision and owner epoch. The producer partitions current projected-message token estimates into mutually exclusive categories, with incomplete-tool-group protection taking precedence over selected candidate, then active summary, then retained. Candidate is advisory compression guidance, not all eligible content or permission to delete. Compressed means the current summary's size, never the removed original's size. Retained includes other content, not proven-safe content. Historical savings cannot manufacture candidate volumes.
- The status-bar map fits those estimates to SDK occupancy: when their total exceeds observed occupied tokens all estimates scale down uniformly; otherwise the unclassified occupied remainder (including system/tool overhead) joins retained/other. Free capacity still comes from SDK usage, not the DCP estimate. Small category shares remain represented within split cells. A missing/invalid DCP snapshot leaves occupied capacity as neutral gray rather than falsely reporting zero candidates. Missing SDK capacity prevents drawing token proportions even when DCP estimates are available.
- The click-open legend follows the same left-to-right category order as the status-bar track.

## Protocol bridge

- Desktop uses the private `pix/session/runtime_status` ACP request.
- The request accepts `sessionId` plus `refreshModelUsage`; when the latter is false ACP skips provider quota I/O.
- ACP obtains context usage from Pi's public `getSessionStats()` response. Pix's RPC entry augments that response with the DCP extension's live `state.tokensSaved` estimate and cached prepared-projection map when available; a process-local symbol bridge keeps full DCP state private. Reading the bridge does not scan history, recompute candidates, invoke a model, or mutate pruning/compression state. Map production reuses the existing context pass and already-selected candidate.
- Live context changes use the existing private `pix/session-state` notification transport with channel `context-usage`; the payload is Pi's context-usage object (or `null` when unavailable). The same sample is sent on `dcp-tokens-saved` as a non-negative integer (or `null` when DCP is unavailable). ACP samples `getSessionStats()` only at message/compaction boundaries, never for streaming text/thinking deltas.
- A pushed context snapshot advances Desktop's snapshot generation so an older in-flight `runtime_status` response cannot overwrite newer context. An in-flight quota refresh keeps its independent quota generation and may still merge its model-limit fields.
- The same sampled response carries `dcpContextMap` and pushes `dcp-context-map` on the existing session-state transport. Its payload is bounded scalar metadata: positive safe revision, nonnegative safe owner epoch, valid preparation timestamp, and four nonnegative safe integer `tokenEstimates` (`candidate`, `protected`, `compressed`, `retained`) with a positive safe total. Invalid/missing telemetry is explicitly unavailable; transport boundaries allowlist fields. No message bodies or range arrays travel to the UI. Older epoch/revision pushes are ignored; accepted pushes invalidate older pending snapshot responses. Owner changes, reset and shutdown invalidate cached telemetry and prevent stale context passes republishing it.
- DCP details use a separate private `pix/session/dcp_stats` request. ACP reads Pi's flat append-order entries through the async `getEntries()` RPC and derives the active root-to-tip branch in memory from `parentId` links, passing that branch into the shared Pix TUI DCP formatter. This avoids synchronous full-JSONL traversal in the ACP event loop and the nested `get_tree` response, whose recursive JSON serialization overflows the RPC process stack on deeply chained linear sessions.
- Session spend uses the separate private `pix/session/usage` request. ACP aggregates all persisted billed entries from the flat `getEntries()` response, including abandoned branches, because provider billing is not undone by a fork/rewind. The request never performs provider quota I/O.
- Manual compression reuses the DCP extension's `/dcp compress` entrypoint; no additional Desktop-only compression protocol is introduced.
- Model quota refresh reuses the shared Pix model-usage module, including provider auth/refresh behavior.
- API-key Anthropic rate limits use only in-process response-header observation from the owning Pi session. Sessionless draft config has no Messages response to observe and does not synthesize API-key limits; the five-minute refresh never probes a separate Anthropic API-key usage endpoint.
- The response marks model-usage refresh as `skipped`, `ready`, `unavailable`, or `failed` so Desktop can distinguish stale-preserving transient failures from unsupported/unavailable quota data. An `unavailable` refresh may additionally carry `modelUsageCredentialPending: true`, set only when the active route is `pi-claude-code-provider` and no usable local credential exists; it is a transient per-response retry hint that Desktop does not persist into merged status snapshots.
- The private `pix/session/claude_quota_refresh` request accepts `{ sessionId }` for a live Claude Code route and returns the post-nudge quota result plus whether the CLI launched; the optional model usage is fresh on `ready` or explicitly stale on credential-pending `unavailable`. A bounded client timeout exceeds the child timeout plus quota lookup.
- The private sessionless `pix/session/draft_config` request may additionally carry the staged `modelRef`, `thinkingLevel`, and `refreshModelUsage=true`. Its response returns the same model-usage refresh/status shape used by runtime status while remaining workspace-scoped and sessionless.

## Risks / compatibility

- If Pi cannot provide the active tree, or if the shared Pix formatter is unavailable in a standalone ACP build, Desktop still receives context usage and quota status while the DCP popover reports telemetry as unavailable.
- Quota providers may fail because of network/auth state. Such failures are intentionally best-effort status-chrome concerns and do not fail the active chat session.
- Claude Code may change its Keychain service name, custom config Keychain derivation, credential shape, or the undocumented usage endpoint. No blocking Keychain command runs on the main thread; the external security utility may still request macOS Keychain authorization when the credential is protected.
