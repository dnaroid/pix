# Предложение: чекпоинты и откат кода

Статус: предложение для согласования. Это не утверждённая архитектура и не разрешение на реализацию. Меняет действующий контракт [Desktop user-message actions](../../desktop/conversations/desktop-user-message-actions.md), поэтому до реализации нужен отдельный decision record.

[Назад к разделу](index.md) · [Аудит](feature-audit.md)

## 1. Что уже есть

- **Undo changes** откатывает ветку сессии к выбранному user entry и в обратном порядке откатывает записанные мутации (`src/bundled-extensions/workspace-undo/index.ts`, `src/app/workspace/workspace-undo.ts`).
- Владелец мутации определяется на `tool_execution_start`, поэтому steering-сообщение не может перехватить уже запущенную мутацию.
- Журнал хранится как скрытые custom entries `pix-workspace-mutation` в JSONL сессии. Параллельные сессии ведут свои журналы независимо.
- Записываются `Write` (before/after content) и патчи от `Edit` / `apply_patch` / `ast_apply`.
- Откат оптимистичный: изменённый кем-то файл считается конфликтом и не перезаписывается. При частичном сбое уже откаченные мутации применяются обратно.
- По контракту откат не использует `git reset` / `restore` / `checkout` и не выводит владельца из состояния рабочего дерева.

## 2. Пробелы

| Пробел | Последствие | Как у CC / Codex |
|---|---|---|
| **G1.** Мутации через Bash не записываются (`rm`, `mv`, `sed -i`, кодогенерация, форматтеры, `npm install` правит lock-файл) | Undo молча оставляет часть изменений хода | CC тоже не отслеживает Bash. В Codex `/undo` опирается на git-снимки рабочего дерева. |
| **G2.** Нет отката «только код» | Чтобы вернуть файлы, приходится откатывать разговор | В CC rewind есть варианты: код + диалог, только диалог, только код |
| **G3.** Нет предпросмотра | Пользователь не видит заранее, какие файлы изменятся и где будут конфликты | CC показывает список изменённых файлов перед восстановлением |
| **G4.** В транскрипте нет сводки изменений по ходу | Трудно выбрать точку отката | — |

## 3. Предложение

### 3.1. Режимы восстановления (G2) — первый этап, малый риск

Меню user-сообщения разделяет действия:

- **Edit and resend** — без изменений, только история.
- **Undo changes** — без изменений: история + код.
- **Restore code only** — новое действие. Без `navigateTree` применяет тот же план мутаций (выбранное сообщение и все последующие на активной ветке) через существующий `revertWorkspaceMutations`. Сессия остаётся на месте. В неё добавляется скрытая запись `pix-workspace-restore` со ссылками на откаченные мутации, чтобы повторный Undo не применял их второй раз.

Новое действие — единственное расширение меню. Это противоречит пункту контракта «exactly five actions», поэтому контракт придётся поправить.

### 3.2. Предпросмотр (G3)

У bridge-команды появляется dry-run. Она возвращает план по файлам: `revertible` / `conflict` / `unrecorded` (подробнее в 3.3). Desktop показывает компактный диалог со списком файлов и счётчиками. По клику на файл открывается существующий diff-просмотр. Применение начинается только после подтверждения. Между dry-run и применением план может устареть, поэтому при применении проверки конфликтов выполняются заново. Предпросмотр не даёт никаких гарантий.

### 3.3. Запись Bash-мутаций (G1) — главный риск

**Механизм.** На `tool_execution_start` для shell-инструментов (`bash`, alias `Bash`, `shell`) снимается быстрый отпечаток рабочего дерева. На `tool_execution_end` снимается второй. По разнице записывается мутация нового типа `snapshot`: для каждого изменённого файла сохраняются путь, before/after hash и ссылка на blob (или признак «создан» / «удалён»).

**Хранилище blob'ов.** Отдельный shadow-репозиторий вне проекта: `~/.pi/agent/checkpoints/<project-hash>/` с `--git-dir=<shadow> --work-tree=<cwd>`. Основной `.git` не трогается: никаких объектов, refs и индекса, так что Source Control и `git gc` пользователя не затронуты. В JSONL сессии хранятся только hash'и, а не содержимое.

**Дешёвый путь.**

1. Команды, которые `shell-command-policy.ts` классифицирует как read-only, снимков не требуют.
2. Отпечаток строится по `git status --porcelain=v2 -z --untracked-files=all` и `stat` (mtime/size) только для кандидатов. Содержимое записывается в shadow-репо только для файлов, которые реально изменились.
3. Лимиты: размер файла, число файлов на вызов, бинарные файлы. Всё сверх лимита помечается как `unrecorded` и в предпросмотре показывается как «нельзя откатить».
4. Каталоги из `.gitignore` (например `node_modules`, `dist`) не записываются и не откатываются. Это часть контракта, а не ошибка.

**Откат.** Такой же оптимистичный, как для `Write`: файл восстанавливается до before, только если текущий hash совпадает с after. Удалённый файл восстанавливается, только если путь сейчас не существует.

**Параллельные сессии.** Это главный нерешённый риск. Если за время Bash-вызова другая сессия (или пользователь) изменила файл, разница будет ошибочно приписана этому вызову. Защита от перезаписи (сравнение hash) сохраняется, но позже Undo может откатить чужое изменение, если его никто не трогал. Варианты:

- (a) общий для проекта реестр активных мутирующих вызовов (lock-файл в `.pi/` с pid и session id). Запись, сделанная при пересечении с чужим вызовом, помечается `ambiguous`, и такие файлы в предпросмотре по умолчанию сняты с отката;
- (b) приписывать вызову только пути, которые упоминаются в команде. Это ненадёжно;
- (c) принять риск и полагаться на предпросмотр.

Рекомендация: (a) + предпросмотр.

### 3.4. Сводка изменений по ходу (G4, опционально)

Под ответом ассистента показывается строка «изменено N файлов (+a −b)», собранная из журнала мутаций хода. Клик открывает список файлов. Отдельная точка «чекпоинта» не нужна: якорем остаётся user entry.

## 4. Не входит в предложение

- Откат по Git HEAD / index / stash и любые операции с основным `.git`.
- Отслеживание изменений от внешних процессов вне инструментов агента: dev-серверы, пользователь в редакторе, [фоновые процессы](background-shell.md) после завершения вызова.
- Автоматическое слияние конфликтов.

## 5. Риски и стоимость

- Задержка каждого мутирующего Bash-вызова растёт на два `git status`. На больших монорепах это нужно измерить до включения по умолчанию. Предусмотреть настройку `checkpoints.bash: "auto" | "off"`.
- Shadow-репозиторий растёт. Нужна политика очистки: blob'ы, на которые нет ссылок из живых сессий, удаляются по TTL. Сессии удаляются отдельно от проекта, поэтому сборщик должен быть устойчив к ссылкам на отсутствующие blob'ы: такой откат даёт `unrecorded`, а не ошибку.
- Двойной учёт: `Write` / `Edit`, вызванные из `codemode` внутри Bash, на практике не пересекаются, но патч и snapshot одного файла в одном вызове нужно дедуплицировать.

## 6. Проверка (при реализации)

- Детерминированные тесты: Bash create/modify/delete → Undo; конфликт после параллельной правки; `ambiguous` при пересекающемся вызове; Restore code only + последующий Undo без двойного применения; dry-run и применение после изменения файла между ними.
- Существующие `tests/workspace-undo*.test.ts` и `acp/test/agent.test.ts` должны оставаться зелёными.
- Бенчмарк задержки снимка на репозитории Pix и одном большом репозитории.

## 7. Открытые вопросы

1. Включать запись Bash по умолчанию или opt-in на первом этапе?
2. Нужна ли «Restore code only» в TUI сразу или только в Desktop?
3. Где хранить shadow-репозиторий: в `~/.pi/agent/` (переживает удаление проекта) или в `.pi/` проекта (удобнее чистить)?
