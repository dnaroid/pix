# Предложение: фоновые shell-процессы

Статус: реализовано, исторический документ. Действующий контракт: [Background shell jobs](../../tools/background-shell.md). Открытые вопросы раздела 6 решены так: `notifyOnExit` по умолчанию `context`; `shell_input` нет; интеграции с вкладкой терминала нет; bind на `0.0.0.0` разрешён с видимым предупреждением; лимит 8 заданий на сессию, `max_runtime` только по запросу.

[Назад к разделу](index.md) · [Аудит](feature-audit.md)

## 1. Проблема

Агент не может запустить dev-сервер, watch-сборку или долгий тестовый прогон и продолжить работу. Сейчас у него есть только два варианта: заблокировать ход до таймаута или запустить процесс через `nohup … &` с ручными pid-файлами. Во втором случае процесс никто не убьёт, его вывод не попадёт в транскрипт, а после закрытия сессии остаются сироты.

Текущее состояние:

- `Bash` в `external/pi-tools-suite/src/model-tools/index.ts` объявляет `run_in_background`, но отклоняет его: «Unsupported by this adapter».
- Встроенный bash из SDK (`createBashToolDefinition`, `BashOperations.exec` в `core/tools/bash.d.ts`) синхронен в рамках вызова, хотя поддерживает стриминг (`onData`), `AbortSignal` и `timeout`.
- Терминал и package-scripts в Desktop — пользовательские механизмы, у агента к ним доступа нет.

## 2. Предложение

### 2.1. Инструменты для модели

| Инструмент | Назначение | Результат |
|---|---|---|
| `Bash` с `run_in_background: true` (и аналогичный параметр у `bash` / `shell`) | Запуск задания | Сразу возвращает `job_id`, pid, путь к логу и первые строки вывода, если они появились за короткое окно (например 1–2 с) |
| `shell_output(job_id, { since?, filter?, max_bytes? })` | Новый вывод с последнего чтения (курсор хранится на сервере) | Статус `running` / `exited(code)` / `killed`, текст, признак усечения |
| `shell_kill(job_id, { signal? })` | Остановка всей группы процессов | Итоговый статус |
| `shell_jobs()` (или режим `shell_output` без `job_id`) | Список заданий сессии | id, команда, возраст, статус |

Имена согласуются с alias-слоем `model-tools`: Claude-стиль `BashOutput` / `KillShell` можно добавить как alias'ы.

### 2.2. Менеджер заданий

- Новый модуль suite (рабочее имя `background-shell`) с реестром заданий **на сессию**. Ключ — session id, а не процесс, поэтому несколько ACP-сессий в одном процессе изолированы.
- Запуск: `spawn` с `detached: true`, чтобы появилась отдельная группа процессов. Kill отправляет сигнал `-pgid`: сначала SIGTERM, через тайм-аут SIGKILL.
- Окружение, `cwd`, workdir-гранты (`/shell-workdir`) и проверки `shell-command-policy.ts` берутся те же, что у синхронного bash. Выполнение переиспользует `createLocalBashOperations` / `spawnHook`, где это возможно. Фоновый режим не должен стать обходом политики.
- Вывод пишется в кольцевой буфер в памяти (например 256 KB на задание) и полностью в лог `.pi/artifacts/background-shell/<session>/<job>.log` по [правилам артефактов](../../operations/harness-artifact-storage.md). Модель читает буфер, а лог доступен пользователю.
- Лимиты: не больше N одновременных заданий на сессию (например 8) и опциональный `max_runtime`.

### 2.3. Жизненный цикл и очистка

- `session_shutdown` убивает все задания сессии. Выход ACP-процесса (`exit`, SIGTERM, SIGINT) делает то же синхронно, насколько возможно.
- Pid-файл задания хранится рядом с логом. На `session_start` сироты от упавшего процесса находятся по pid + время старта + команда (защита от переиспользования pid) и показываются пользователю, а не убиваются молча.
- Отмена хода (Escape) **не** убивает фоновые задания: они переживают ход по определению. Отдельная команда Desktop/TUI «Stop all background jobs» есть.
- Fork или смена сессии: задания остаются за исходной сессией и не наследуются форком.

### 2.4. Уведомление агента о завершении

Когда задание завершилось, а сессия в этот момент выполняет ход, на ближайшей границе (`turn_end` / `agent_before_settle`) добавляется короткая custom-запись: «job X exited with code N, last lines…». Если сессия простаивает, запись показывается в UI **без** `triggerTurn`: автоматического продолжения агента нет, пользователь решает сам. Настройка `backgroundShell.notifyOnExit: "context" | "ui-only" | "off"`.

### 2.5. Desktop и TUI

- В статусе сессии появляется индикатор «N jobs». Поповер показывает список с хвостом вывода, кнопками Kill и «Open log».
- ACP: приватное расширение-уведомление о смене статуса задания. Транскрипт рендерит вызов `Bash` с `run_in_background` как обычный tool call с бейджем job id.
- Тяжёлое чтение логов не выполняется в UI-потоке.

## 3. Безопасность

- Политика команд та же, что у синхронного bash. Отдельно стоит решить, нужно ли подтверждение для фоновых сетевых серверов (bind на `0.0.0.0`) — это открытый вопрос.
- Секреты в выводе проходят через существующий `credential-firewall` при отдаче модели, как и синхронный вывод.

## 4. Риски

- Утечки процессов. Это главный риск, нужны детерминированные тесты очистки.
- Гонки: kill во время spawn; вывод, пришедший после `session_shutdown`; `shell_output` для задания уже закрытой сессии; завершение задания во время compaction.
- Shell-вывод на Windows для CI не нужен: Desktop поддерживается только на macOS, но код suite должен оставаться переносимым или явно отключаться на win32 (см. `ci-reliability`).

## 5. Проверка (при реализации)

- Unit-тесты менеджера: start → output-курсор → exit-код; kill группы с дочерним `sleep`; лимит заданий; shutdown убивает всё; сирота найдена после симулированного краха.
- Тест, что `run_in_background` проходит те же проверки политики и workdir.
- Desktop: индикатор и kill через ui-qa после реализации.

## 6. Открытые вопросы

1. Режим уведомления по умолчанию: `context` или `ui-only`?
2. Давать ли модели `shell_input(job_id, text)` для интерактивных процессов? Предлагается нет, это вне MVP.
3. Нужна ли интеграция с терминалом Desktop: «открыть задание во вкладке терминала»?
