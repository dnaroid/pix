# Desktop runtime context and model limits

<!-- markdownlint-disable MD013 -->

## Type

Change

## Lifecycle

Active implemented contract.

## Goal

Bring the TUI's context-usage, prepared DCP context-map, and current-model quota signals into Pix Desktop without copying terminal presentation into the GUI. Desktop keeps durable DCP statistics as a separate protocol capability while rendering the live context state as dense IDE status chrome and lightweight click-open panels.

Decision: [Status-bar click popups](../decisions/0048-status-bar-click-popups.md), superseding [hover details](../decisions/0037-status-bar-hover-details.md) for interaction only. Session-pane removal: [0047](../decisions/0047-remove-session-inspector.md).

## Behavior

- Usage remains in the left status group. The right group places Observer (radar), Subagents, then Plan, with no short vertical separators between groups. The status-bar top border remains; dividers inside popups and context-ring sector separators are unchanged.

- Status-bar elements and their detail surfaces do not use browser-native `title` tooltips. Accessible labels remain. Usage shows recorded session spend, an integrated weekly cycle/remaining-quota timeline and a short-window Limits scale, not quota-description paragraphs; compact quota indicators remain in its trigger. See [quota limits](desktop-quota-calendar.md) and [decision 0039](../decisions/0039-quota-reset-calendar.md). Context, Usage and Observer popup lower edges match Plan, touching the top of their triggers with no visual gap. Sidebar tooltips are unchanged.

- Once an active Desktop session runtime is ready, the status bar shows a slightly extended horizontal capacity track without an inline numeric percentage.
- Compact status chrome labels context as `Context`, omits redundant hourly/weekly and `resets` text (window names and reset meaning remain in click details), and shows Claude Code provider model names without the `Claude Code ` prefix in the model/thinking display. Persistent model names use neutral foreground text and thinking uses muted text, leaving provider brand color to the icon; picker and usage-detail model colors are unchanged. Provider IDs and routing are unchanged. Context and quota use content-sized grid groups rather than equal columns; bounded inline controls clip excess content at very narrow widths instead of painting over neighboring controls, while detail panels remain unclipped.
- Context and Usage have distinct inter-group spacing and fixed inner telemetry slots. Quota windows use track, reset countdown, then the associated warning/retry/cache indicator, with no bullet or middle-dot separators; loading placeholders follow the same order. Only actually present quota windows take space; the account label stays in the details rather than the trigger.
  Neither Context nor quota triggers reserve or render numeric percentage slots, including their skeleton placeholders. Percentages remain available in detail panels and quota accessible descriptions; narrow-window clipping remains bounded by the outer control.
- Context detail-panel danger thresholds match the TUI on the numeric percentage only: up to 30% is the normal/success range, 31–50% warning, and above 50% error. Desktop renders the normal numeric percentage in neutral light gray instead of success green; warning/error keep their semantic colors. The progress track keeps its existing capacity/DCP category coloring.
- When a prepared DCP context map is available, the occupied portion of the status-bar track remains categorically colored for other/retained content, compression candidates, protected incomplete tool groups, and current summaries; free capacity remains visually separate. Activating the context button opens a compact non-modal panel with absolute context tokens/current window, an enlarged full-width version of the same capacity track, and a compact color legend with approximate category token volumes. The panel preserves the status-bar track's unknown/occupied/free semantics and uses the same live context map without loading durable statistics. The live DCP `tokensSaved` estimate is also shown directly in the status bar when positive; zero or unavailable savings reserve no inline savings slot, while an available zero remains in the accessible description and Context details. The saved value is the extension's running estimate of context removed by pruning/compression, not the durable statistics report's measured commit gain and not a billing counter.
- The Context panel replaces the former click-open DCP statistics surface in the status bar. Opening it performs no durable DCP statistics request and exposes no compression action. The underlying DCP statistics request and `/dcp compress` runtime capability remain available to other consumers, but are no longer attached to this status-bar interaction.
- In Context details, available zero savings use the neutral label `DCP savings` with muted text and a neutral border, without a success-colored background. Only positive savings use `DCP saved you` and success coloring; unavailable savings omit this row.
- All status-bar detail popups open only on native button activation (click, Enter or Space), never hover or mere keyboard focus. Repeated activation toggles them closed. Pointer departure does not dismiss them; outside pointer interaction, focus leaving the trigger/panel region and Escape do. Escape restores trigger focus. Context and Usage are mutually exclusive. Session switches remount the session-specific surfaces so old open panels cannot follow another session. Panels retain gap-free lower edges, semantic Desktop popover/chrome tokens and non-modal behavior; no hover-dismiss timer remains.
- When the active model/provider exposes account quota data, the status bar shows hourly and/or weekly compact remaining-quota tracks and reset countdowns without inline numeric percentages. All compact quota fills (including header-derived rate windows) are anchored right: remaining quota is filled on the right, consumed quota is empty on the left, matching the hourly and weekly popup tracks. Context capacity orientation is unchanged. Weekly tracks are divided into seven equal day slices; their hover text labels those slices from the reported window timing. The provider still supplies one aggregate weekly remaining percentage, so the UI does not invent per-day usage values.
- Anthropic subscription OAuth (`sk-ant-oat…`) retains its five-hour/seven-day quota lookup and takes precedence over response-derived usage. With a regular Anthropic API key (`sk-ant-api…`), Pix instead observes `anthropic-ratelimit-*` headers on actual Messages API responses. It displays the lowest remaining percentage among valid request, input-token, output-token, and token limits as one short-window rate-limit indicator, using that limit's own RFC 3339 reset time and a descriptive rate-limit label rather than presenting it as a five-hour subscription quota. Missing or malformed limits do not create a status; no extra request is made for API-key usage, and this short window does not participate in daily-budget warnings.
- Models routed through `pi-claude-code-provider` use Claude Code's own subscription credential for the same five-hour/seven-day quota lookup, independently of Pi's `anthropic` auth classification. Pix reads the current `claudeAiOauth` token from Claude Code's macOS login Keychain service (including the per-directory service for `CLAUDE_CONFIG_DIR`) or its `.credentials.json` fallback only for quota polling; it never refreshes or writes Claude Code credentials or includes tokens in Desktop/ACP status. A Keychain entry that is present but expired, malformed, or not an OAuth token falls through to the `.credentials.json` fallback instead of masking it, because Claude Code refreshes the two copies at different times and either may hold the current login. Expired or absent credentials in both locations yield unavailable quota until Claude Code refreshes them; the last successfully observed quota can remain visible only as explicitly **stale** cache, with each window removed at its own reset (never as a fresh observation). The cache belongs to the Claude Code route and is not copied into a different provider's status; ordinary unavailable quota with a present credential still clears the display. While the Claude Code credential is absent, quota polling retries at a bounded faster cadence (~30–60s) instead of waiting for the five-minute interval: those retries read only the Keychain/credentials file and perform no provider network request, so quota appears within about a minute after Claude Code refreshes its login. The faster cadence is armed only for credential-absent unavailability (Desktop recognizes it through the response's `modelUsageCredentialPending` flag); when a token exists, an empty endpoint response keeps the regular cadence. Pix follows the adapter's restricted Claude child environment, which does not forward Pi's API key or OAuth-token environment variables. This is an opt-in-to-provider, best-effort integration with Claude Code's credential format and Anthropic's undocumented OAuth usage endpoint, not a supported Claude Code quota API.
- Claude Code's structured `rate_limit_event` notices also update the current runtime's saved quota immediately, without parsing displayed warning text or issuing credential/quota requests. In addition to warning/rejection notices, the provider parses `rate_limit_info.unifiedWindows` when present (observed in Claude Code 2.1.300; an undocumented CLI field that may change or disappear, so its absence is not an error); its `five_hour` and `seven_day` utilization/reset samples are emitted on every event, including status `allowed`. Each valid window is handled independently, malformed/partial windows are dropped, utilization outside its valid range is rejected, and CLI second-based resets are normalized to milliseconds. Allowed-window telemetry updates quota but never produces a user-visible warning. The `pix:claude-code:rate-limit` version-1 sample therefore accepts status `allowed` alongside `allowed_warning` and `rejected`; `allowed` and `allowed_warning` require `utilization`, while `rejected` may omit it. An `allowed` sample cannot lift a rejection: within the same reset the window stays at 0% remaining until a newer reset supersedes it. Valid warning windows provide utilization and a reset; rejection sets the reported window to 0% remaining. Within the same reset, observed consumption cannot decrease and an older endpoint reply cannot raise remaining quota over a newer sample/rejection. A newer authoritative endpoint reading for the same reset window (within reset-precision tolerance) supersedes the streamed sample, allowing a provider-granted early reset to lower displayed usage. CLI whole-second resets and endpoint fractional-second resets within one second represent the same window. A newer authoritative reset supersedes the sample; an estimated reset synthesized for a null endpoint reset is not rollover evidence. Expired samples no longer override polling. Partial notices preserve the other window and reset-credit metadata. The extension publishes versioned, secret-free `pix:claude-code:rate-limit` telemetry before warning deduplication; ACP validates the originating Pi session/model and pushes a quota-only `claude-code-usage` snapshot, separate from Anthropic API-key header usage and context/DCP snapshots. Once accepted, a sample is account-wide rather than session- or model-owned: subscription quota belongs to the Claude Code login, so ACP pushes the merged snapshot to every live session whose active model is a `pi-claude-code-provider` route (any model), and TUI applies it to the visible Claude Code route regardless of which session observed it. Closing or replacing a session does not discard these samples; each window expires only at its own reset. Non-Claude Code routes never receive them. Samples are shared within one Pix process only (Desktop's ACP agent or one TUI); separate processes converge through their own events and polling. Limitation: this assumes a single Claude Code account per process. With account rotation enabled, samples carry no account identity, so one account's consumption could be shown for sessions running on another account until polling or that account's next event corrects it; supporting rotation requires adding an account identifier to the telemetry and keying the cache by it. Web search does not publish window telemetry. Older CLI versions that omit `unifiedWindows` continue to rely on polling, warnings, and the 429 fallback.
- If a request instead ends with the exact Claude CLI English `You've hit your session limit · resets … (IANA timezone)` 429 error, the bundled quota-wait extension publishes the same rejected five-hour telemetry for the current session/model. This narrow fallback accepts only an unambiguous future local reset within five hours; generic 429s, weekly/overage errors, unknown formats and ambiguous/nonexistent DST clocks do not infer quota. Its minute-precision reset is matched within one minute until structured telemetry supplies a precise reset. It performs no credential/quota I/O and never parses the displayed notification.
- Observed rate limits belong to the session and request model that produced the response. Switching models or sessions (including concurrent Desktop runtimes) cannot reuse a previous model/session's response headers. An accepted response updates active usage promptly rather than waiting for five-minute provider polling; closing/replacing a session invalidates its captured limits and stale callbacks.
- Model-limit detail color thresholds match the TUI on the numeric percentage only: below 20% remaining is error, below 50% remaining is warning, otherwise the normal/success range. Desktop renders that normal numeric percentage in neutral light gray instead of success green; warning/error keep their semantic colors. Quota progress fills remain neutral gray. Desktop and TUI show a warning triangle when account-wide consumption exceeds the cumulative daily budget for a known window longer than 24 hours. Days are consecutive 24-hour slices anchored to `resetAt - windowSeconds`, not local calendar dates. The whole current day's allowance is available immediately, with unused allowance carried forward: budget percent is `min(100, (floor(elapsedSeconds / 86400) + 1) * 86400 / windowSeconds * 100)`. Consumption must strictly exceed this budget; equality does not warn. A seven-day window allows 1/7 on day one, 2/7 on day two, and the whole quota on day seven. There is no minimum elapsed-time or consumption gate. Unknown/short windows, future windows, passed resets and zero remaining quota do not show this triangle. The semantic warning color remains independent of the numeric percentage color. This is a pacing signal, not measured per-day usage or an automatic pause.
- Activating `Usage` opens the on-demand session-spend popover defined in [session-usage.md](session-usage.md); it does not force a provider quota refresh. The popover is a compact `provider → model → tokens · cost` breakdown. Parent-agent, async-subagent, retry, and fallback calls are merged into the model that actually incurred them. Model names use the normal Pix model colors. The session-spend breakdown does not show provider/session-share percentages or a separate agent/subagent subtotal; the integrated weekly cycle/remaining-quota timeline and short-window Limits scale show account telemetry, and a per-model token donut may summarize recorded token shares in the same Usage surface. The popup weekly fill is neutral foreground (white in dark mode), unlike the muted remaining-quota trigger fill; its pin moves from start left to reset right. For a ready session whose active route uses `pi-claude-code-provider`, it additionally offers an explicit **Refresh limits** control; drafts and other routes do not show it. Clicking this control launches one bounded, headless Claude CLI login nudge asynchronously, discards its output, then rereads Claude Code's local credential and queries Pix's normal quota endpoint. It does not parse undocumented CLI output into quota, refresh recorded session spend, or block the UI. Duplicate clicks/sessions share at most one Claude child; the button is disabled while that session is refreshing. Failures show a retryable message, preserving cached quota only according to the stale-window rule above.
- Normal model-quota refresh still happens when the active runtime/model changes and every five minutes. The `Usage` control remains available while a prompt or quota refresh is running because reading recorded spend is independent of provider quota I/O. Credential-pending Claude Code retries run per session (runtime and draft) while responses keep flagging a missing local credential; forget/reset and a superseded draft selection cancel them. Separately, a live runtime whose initial quota lookup fails (including rejected status transport or a failed quota reread after the startup login nudge) retries ordinary quota reads after bounded delays of 5, 15 and 30 seconds, instead of waiting five minutes. These retries never launch the CLI. A ready quota, ordinary unavailability without a pending-credential hint, or usable pushed header telemetry ends this startup recovery; snapshot-only replies do not. The three-retry budget is per runtime owner and does not restart on later periodic failures. Newer quota/manual requests cancel a pending timer; forget/reset cancel it and rearm the budget for a new owner. Client replacement, readiness loss and superseded quota generations cannot issue an old owner's retry. Draft failure cadence is unchanged.
- On a live runtime's first authoritative quota check, Claude Code credential-pending unavailability automatically starts the same bounded background CLI login nudge and quota reread as **Refresh limits**, without delaying runtime activation or context updates. Ready credentials, other providers, unsupported quota, failed lookup, snapshot-only replies and superseded replies do not launch a CLI. Startup recovery is attempted once per runtime owner; an explicit manual refresh also consumes that attempt. If credentials remain missing after recovery, only the existing local-credential retry cadence continues; no repeated automatic CLI launches occur. Forget/reset rearm startup recovery and invalidate old completions. Window teardown disposes the ACP connection without its `onDisconnect` callback, so lifecycle teardown runs the same reset-after-disconnect explicitly (immediately and again once disposal settles), cancelling credential/startup retry timers and side-conversation state. Sessionless drafts never launch this startup nudge. This best-effort nudge uses Claude Code's own login and may perform a model round trip; it does not sign an unauthenticated user in or guarantee immediate quota availability.
- Desktop status chrome does not repeat workspace identity or the current Git branch. Project identity remains available in the titlebar/project switcher, and branch information remains in Source Control. Removing the status-bar identity also removes the dedicated 30-second branch-only polling path; Git state continues to refresh through Source Control and the existing sidebar indicator mechanisms.

Steps retains the `Clear session steps` action backed by the session-owned pending guard and ACP request. Its bounded scrollable list centers the current item on click opening with `in_progress` → `pending` → `deferred` priority. Subagent popups keep the fixed identity/status header and model/activity footer around a scrollable task body. Empty sessions render no activity controls. Pushed activity snapshots remain independent of quota/context polling. See [Session activity](../desktop/conversations/desktop-session-sidebar.md).
- The right Session inspector, its opening command, preference and width persistence are removed; status-bar popups are the live detail surfaces. The workspace sidebar and session list are unchanged.
- The compact status-bar context track is the always-visible DCP capacity visualization. Total occupied/free capacity comes only from the already-held live SDK `tokens` and positive `contextWindow` denominator; the separately reported percentage is not a denominator. Invalid or unknown context produces neutral unknown capacity rather than invented free space, and over-capacity samples fill the bounded track while retaining their actual textual percentage.
- Within occupied capacity, DCP category volumes are explicitly **approximate**, from a dated **last prepared DCP projection** carrying a runtime revision and owner epoch. The producer partitions current projected-message token estimates into mutually exclusive categories, with incomplete-tool-group protection taking precedence over selected candidate, then active summary, then retained. Candidate is advisory compression guidance, not all eligible content or permission to delete. Compressed means the current summary's size, never the removed original's size. Retained includes other content, not proven-safe content. Historical savings cannot manufacture candidate volumes.
- The status-bar map fits those estimates to SDK occupancy: when their total exceeds observed occupied tokens all estimates scale down uniformly; otherwise the unclassified occupied remainder (including system/tool overhead) joins retained/other. Free capacity still comes from SDK usage, not the DCP estimate. Small category shares remain represented within split cells. A missing/invalid DCP snapshot leaves occupied capacity as neutral gray rather than falsely reporting zero candidates. Missing SDK capacity prevents drawing token proportions even when DCP estimates are available.
- The click detail legend follows the same left-to-right category order as the status-bar track.

## Protocol bridge

- Desktop uses the private `pix/session/runtime_status` ACP request.
- The request accepts `sessionId` plus `refreshModelUsage`; when the latter is false ACP skips provider quota I/O.
- ACP obtains context usage from Pi's public `getSessionStats()` response. Pix's RPC entry augments that response with the DCP extension's live `state.tokensSaved` estimate and cached prepared-projection map when available; a process-local symbol bridge keeps full DCP state private. Reading the bridge does not scan history, recompute candidates, invoke a model, or mutate pruning/compression state. Map production reuses the existing context pass and already-selected candidate.
- Live context changes use the existing private `pix/session-state` notification transport with channel `context-usage`; the payload is Pi's context-usage object (or `null` when unavailable). The same sample is sent on `dcp-tokens-saved` as a non-negative integer (or `null` when DCP is unavailable). ACP samples `getSessionStats()` only at message/compaction boundaries, never for streaming text/thinking deltas.
- A pushed context snapshot advances Desktop's snapshot generation so an older in-flight `runtime_status` response cannot overwrite newer context. An in-flight quota refresh keeps its independent quota generation and may still merge its model-limit fields.
- The same sampled response carries `dcpContextMap` and pushes `dcp-context-map` on the existing session-state transport. Its payload is bounded scalar metadata: positive safe revision, nonnegative safe owner epoch, valid preparation timestamp, and four nonnegative safe integer `tokenEstimates` (`candidate`, `protected`, `compressed`, `retained`) with a positive safe total. Invalid/missing telemetry is explicitly unavailable; transport boundaries allowlist fields. No message bodies or range arrays travel to the UI. Older epoch/revision pushes are ignored; accepted pushes invalidate older pending snapshot responses. Owner changes, reset and shutdown invalidate cached telemetry and prevent stale context passes republishing it.
- DCP details use a separate private `pix/session/dcp_stats` request. ACP reads Pi's flat append-order entries through the async `getEntries()` RPC and derives the active root-to-tip branch in memory from `parentId` links, passing that branch into the shared Pix TUI DCP formatter. This avoids synchronous full-JSONL traversal in the ACP event loop and the nested `get_tree` response, whose recursive JSON serialization overflows the RPC process stack on deeply chained linear sessions.
- Session spend uses the separate private `pix/session/usage` request. ACP aggregates all persisted billed entries from the flat `getEntries()` response, including abandoned branches, because provider billing is not undone by a fork/rewind. The request never performs provider quota I/O.
- Manual compression reuses the DCP extension's `/dcp compress` entrypoint; no additional Desktop-only compression protocol is introduced.
- Model quota refresh reuses the shared Pix model-usage module, including provider auth/refresh behavior.
- API-key Anthropic rate limits use only in-process response-header observation from the owning Pi session. Sessionless draft config has no Messages response to observe and does not synthesize API-key limits; the five-minute refresh never probes a separate Anthropic API-key usage endpoint.
- The response marks model-usage refresh as `skipped`, `ready`, `unavailable`, or `failed` so Desktop can distinguish stale-preserving transient failures from unsupported/unavailable quota data. An `unavailable` refresh may additionally carry `modelUsageCredentialPending: true`, set only when the active route is `pi-claude-code-provider` and no usable local credential exists; it is a transient per-response retry hint that Desktop does not persist into merged status snapshots.
- The private `pix/session/claude_quota_refresh` request accepts `{ sessionId }` for a live Claude Code route and returns the post-nudge quota result plus whether the CLI launched; the optional model usage is fresh on `ready` or explicitly stale on credential-pending `unavailable`. A bounded client timeout exceeds the child timeout plus quota lookup.
- The private sessionless `pix/session/draft_config` request may additionally carry the staged `modelRef`, `thinkingLevel`, and `refreshModelUsage=true`. Its response returns the same model-usage refresh/status shape used by runtime status while remaining workspace-scoped and sessionless.

## Risks / compatibility

- If Pi cannot provide the active tree, or if the shared Pix formatter is unavailable in a standalone ACP build, Desktop still receives context usage and quota status while the DCP popover reports telemetry as unavailable.
- Quota providers may fail because of network/auth state. Such failures are intentionally best-effort status-chrome concerns and do not fail the active chat session.
- Claude Code may change its Keychain service name, custom config Keychain derivation, credential shape, or the undocumented usage endpoint. No blocking Keychain command runs on the main thread; the external security utility may still request macOS Keychain authorization when the credential is protected.
