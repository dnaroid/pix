## Ideas (assumptions and proposals, not facts)

**P2-C1 (critical case)**: Before any engine: dirty worktrees mean no proven pre-edit baseline; child-reported edits don't establish parent authorship; syntax matches prove nothing (brief's own caveats, corroborated by P2-F4/F5). Precision below ~high would make cards noise and burn the Observer's hard-won trust. Cheap options (P2-A3/A4) likely cover most guardrail categories. *Test*: run any candidate detector over this repo's real history; measure findings a maintainer would act on. If unmeasurable, don't build the engine.

**P2-A1 (Alt A, integrated)**: Add code-health as a second Observer card type fed by a file-snapshot delta taken at settle. Benefit: inherits P2-F3's cancellation/budget/freshness machinery wholesale. Risk: violates the active contract ("not a code reviewer", "cannot inspect files independently") — needs an explicit ADR amendment, not silent scope creep; couples two experiments. *Test*: teardown-during-analysis produces no card and no leaked timer.

**P2-A2 (Alt B, standalone)**: Separate extension on `agent_settled` (gated on `agent_before_settle.outcome === completed`, P2-F2), scoped to `getEventPaths` ∪ nested-call paths, results as user-only cards. Decouples from Observer's contract; must re-implement cancellation/dedup correctly (avoid P2-F1's mistake via per-runtime ownership). *Test*: stale settle after branch switch doesn't publish.

**P2-A3 (Alt C, thin hook)**: Generalize comment-checker's pattern: added-lines-only checks (listener/timer/subscription added without teardown in the same hunk; file-size delta nudge) appended to tool_result. Lowest latency risk if kept to in-memory line analysis; but runner awaits handlers sequentially — must stay synchronous-cheap. *Test*: added-line false-positive rate on intentional one-shot `setTimeout`.

**P2-A4 (Alt D, rules primary)**: Curated ast-grep YAML rulepack encoding AGENTS.md guardrails, run only on changed files at settle; LLM only for triage of rule hits, opt-in. Assumption: executable availability (external `pi.exec`, 120 s timeout — `src/ast-grep/tool.ts`); needs capability probe + measured per-rule precision before any default-on. *Test*: rule hits reviewed against known-good lifecycle code in this repo.

**P2-A5 (unconventional: no detector)**: Skip detection entirely; periodically re-inject a compressed guardrail checklist (races/teardown/listeners) as a bounded system nudge at cadence boundaries, mirroring comment-checker's nudge philosophy. Zero infra, zero false positives, zero egress; relies wholly on model self-check — likely weak but a legitimate floor that challenges engine justification. *Test*: A/B whether guardrail violations in review actually drop.

**P2-A6 (unconventional: test-suggestion bridge)**: Detector only classifies risk (changed file touches lifecycle-bearing code), then nudges the user to run existing deterministic tests (e.g., the stale/abort/teardown suites cited in the brief). Ground truth stays in tests; requires project-execution trust akin to `specs/lsp-trust.md`. *Test*: nudge fires for a real `controller.ts` edit, not for docs.

**P2-H7 (finding identity, cross-cutting)**: Stable ID = ruleId + normalized path + symbol anchor; resolution by re-running the rule on a fresh snapshot, never by TTL expiry; suppression lists are durable config, never `.pi/artifacts/` scratch (per `specs/harness-artifact-storage.md`).

All scheduling variants (A1/A2) must be off the agent critical path, opt-in, no auto-fix, no agent continuation — consistent with fixed decisions.

Для всех вариантов исходно — только пользовательский вывод, без изменения tool-result, продолжения агента и исправлений. Нейтральный UI-мост в B не обязан передавать findings в LLM Observer.

## Общие границы экспериментов

**P1-P1. Конвейер актуальности.** Событие mutation, включая вложенное и ошибочное → ограниченная очередь путей → debounce → асинхронный снимок → локальный анализ → проверка версии → публикация. Тяжёлый анализ — вне UI/main thread. Автоматическую публикацию можно отложить до успешного settlement; ручная проверка нужна и после ошибки.

Ключ результата: физический workspace/worktree, правило и версия анализатора, путь, символ/устойчивый якорь; hash снимка — отдельно. Первый post-edit снимок не baseline; `HEAD` тоже не гарантированно baseline. При неизвестной исходной версии показывать состояние, не «ухудшение». Отсутствие результата из-за отмены/ошибки не означает исправление. Rename требует осторожного сопоставления. Shell, внешние writers и потерянные watcher-события требуют ограниченной сверки; гарантировать лишь проверенный снимок и описанное покрытие, не вечную актуальность или авторство агента.

**P1-P2. Разделять доказательства.** Размер файла — детерминированная метрика; функции и ownership-паттерны требуют AST/dataflow; циклы — графа разрешённых зависимостей. Гонки, утечки, deadlock и блокировка UI требуют lifecycle/исполнительного контекста, теста либо runtime-свидетельств. Совпадение синтаксиса — кандидат. «Слишком много ответственностей» — интерпретация, включая LLM-эвристику. Confidence описывать основанием и ограничениями, не выдуманным процентом.

**P1-P3. Контроль против переусложнения.** Сначала сравнить D и E вручную с отсутствием новой функции. Затем C: согласованные языки, несколько правил, локальные метрики, исключения generated/vendor/секретов, лимиты файлов/байтов/CPU/времени; без новых зависимостей. B оправдан только повторно подтверждённой потребностью; глубокие проверки и LLM — позже, отдельно разрешённые. Durable baseline/suppressions не хранить в scratch.

Измерять добавочную полезность сверх LSP, неверные/повторные замечания, время разбора, задержку инструментов и расход ресурсов; пороги согласовать заранее. Тестировать обратный порядок завершений, игнорируемую отмену, частичную запись с ошибкой, удаление/rename, смену сессии, параллельных writers и teardown таймеров/подписок. Сходные lifecycle-сценарии уже представлены в `tests/heads-up-controller.test.ts:156–220`, но это не проверка будущего механизма.

Одобрения нужны для языков, baseline, бюджетов, исполнения конфигурации, хранения и исходящего кода. Передача исходников провайдеру — отдельное согласие; nudge агенту и opt-in gate — отдельные последующие решения.

## P3-P1: from file change to current finding
1. **Collect candidate paths.** Each path is tagged with its source: `tool`, `nested`, `git-status` or `unknown`. A failed tool still counts as a candidate, because it may have partially written.
2. **Snapshot each file:** hash, size and mtime at read time.
3. **Cache analysis** keyed by path, content hash, and analyzer and rule versions.
4. **Give findings a stable identity:** rule, path and a normalized anchor (symbol name or snippet fingerprint, not a line number).
5. **Compute the delta** against the session's first-observed snapshot, labelled "first observed, not pre-edit".
6. **Re-check the hash before display.** If it changed, mark the finding stale or drop it. A delete or move resolves the old path's findings.
7. **Assign ownership** by session and generation. Two sessions in one worktree see each other's changes only as *unattributed*.

## P3-T: failure modes and tests
1. **New prompt during analysis.** A generation bump discards the late result, so no UI write happens.
2. **File edited between hash and display.** The finding is marked stale.
3. **Child process ignores abort.** The parent kills it, keeps the analysis lock, and starts no second run.
4. **Teardown.** Timers, child processes and listeners are released, with nothing writing afterwards. Assert zero active handles.
5. **Two sessions in one worktree.** Attribution is correct and the dedup state is per session (unlike the comment-checker's module-level variable).
6. **Partial write from a failed `apply_patch`.** The file is still analysed.
7. **Delete or move.** The old finding is resolved and no LSP-style `existsSync` skip hides it.
8. **Burst of 50 edits.** One analysis runs per settle; no queue builds up.

### P1-H1 — Тонкий сборщик + существующие анализаторы + пользовательская сводка

Объединяет **P1-C**, **P1-D**, **P3-C**, **P3-E1**.

- Фоновый исполнитель делает ограниченные снимки и запускает только доступные, явно разрешённые проверки. Отсутствующий анализатор означает «не проверено», не установку и не успешный результат.

**Почему помогает:** C обеспечивает событийный вход, D — проверенные специализированные правила, сводка снижает давление карточек. LLM и отдельный брокер не нужны.

### P1-H2 — Обязательства → подходящие тесты → необязательный ratchet

Объединяет **P1-E**, **P2-A6**, **P3-E2**.

Пользователь выбирает несколько обязательств проекта: например, «позднее завершение не меняет новое состояние» или «последний владелец освобождает ресурс». К каждому можно привязать существующий тест и область файлов. После изменения показывается не обвинение, а состояние свидетельства: «связанный тест не выполнялся для этого снимка».

Опциональный следующий слой — согласованный, версионированный ratchet для измеряемых свойств: размер, число зависимостей, новые циклы. Порог и исключения остаются политикой проекта, не универсальной истиной Pix.

**Почему помогает:** связывает слабую эвристику риска с проверяемым действием, не обещая обнаруживать гонки синтаксисом.

**Проверка:** положительный тест относится к точному снимку и области; последующая правка переводит свидетельство в устаревшее. Предложение команды ничего не запускает.

### P1-H3 — Минимальный протокол актуальности, независимый от выбранной архитектуры

Развивает **P1-P1**, **P2-H7**, **P3-P1**, применим к **P1-B** и **P1-H1**.

Разделить три идентичности:

1. **Workspace/worktree** — физическая область файлов.
2. **Анализ** — снимки всех использованных файлов, версии правил и конфигурации.
3. **Доставка** — конкретная сессия, поколение и подписка.

На старте достаточно локального состояния одного runtime; межпроцессное совместное вычисление — отдельное расширение, не обязательство MVP. Закрытие сессии запрещает доставку, но не должно закрывать чужой ресурс.

Статусы различать: актуально для снимка, требует перепроверки, исправлено проверкой, объект удалён, больше не покрывается. Rename может перенести проблему: исчезновение старого пути не доказывает исправление. Перестановка строк не создаёт новую идентичность.

**Проверка:** две сессии, rename, поздний отрицательный результат и смена конфигурации не приводят к ложному «исправлено» или публикации чужого состояния.

### P1-H4 — Общая презентация без общего рассуждающего движка

**Почему помогает:** проверяет пользовательскую ценность интеграции без немедленного объединения lifecycle двух механизмов.

**Проверка:** отключение Observer не выключает локальный отчёт; отключение code-health не меняет историю и бюджет Observer.

## Критическая оценка

### P1-K1 — Фактическая точность не равна полезности

**P3-H1**, **P2-A7**, мой **P1-H1** рискуют построить безошибочный счётчик строк, который никто не использует. Размер и рост не доказывают концентрацию ответственностей; синтаксические вопросы о каждом `Promise` создают шум даже без слова «ошибка».

Сохраняю сводку как эксперимент, но не обязательный первый продукт. Ограничение **P2-C2** «движок только после полезной facts-only сводки» слишком сильное: неудача счётчика не опровергает полезность конкретного AST-правила.

**Опровергающий тест:** отдельно сравнить метрики, одно выбранное правило и журнал обязательств с обычным LSP-процессом. Измерять добавочную полезность, неверные сигналы, время разбора. Replay **P3-H6** оценивает экспертную полезность, но не фактическую долю действий пользователей; для неё нужен будущий добровольный пилот. Включить обычные изменения, а не только известные багфиксы.

### P1-K2 — Baseline отвечает на разные вопросы

**P2-A9** задаёт нормативный baseline: «что разрешено политикой». **P3-H2** предлагает наблюдаемый: «что изменилось с начала наблюдения». Ни один сам по себе не доказывает авторство агента.

«Чистый Git-файл» — условное свидетельство равенства определённому blob, не атомарный снимок workspace. Изменение уже dirty-файла не меняет список dirty-путей. Фильтры, параллельные writers и смена index требуют явных ограничений.

Сохраняю классы происхождения baseline, но слово «ухудшение» допустимо только относительно названной метрики/политики и сопоставимых снимков.

**Опровергающий тест:** повторная shell-правка уже dirty-файла, изменение index во время снимка, неотслеживаемый файл, изменение baseline вместе с кодом. Результат не должен приписывать действия родителю или объявлять отсутствие регрессии при неизвестной базе.

### P1-K3 — Два чистых снимка не доказывают исправление

Уточнение **P2-H8** добавляет задержку, но не устраняет гонку: одинаковые снимки могут быть промежуточными; analyzer мог пропустить область. Для **P1-H3** важнее успешная повторная проверка с достаточным покрытием и версиями всех входов.

Для циклов и dataflow изменение зависимости инвалидирует результат, даже если анализируемый файл неизменен. Ключ кэша только по его hash недостаточен. Rename — «старый объект исчез», не обязательно «дефект исправлен».

**Опровергающий тест:** dependency изменяется при неизменном исходном файле; два одинаковых снимка сменяются поздней записью; parser возвращает неполное покрытие. Нельзя показывать «исправлено» по отсутствию findings.

### P1-K4 — Фоновость и переиспользование не бесплатны

**P2-A11** пока предлагает новый брокер по образцу LSP, а не непосредственное использование готовой абстракции. Он добавляет выбор владельца, межпроцессное доверие и teardown ради ещё не измеренной экономии.

В **P3-H3** даже синхронный просмотр строк остаётся работой на критическом пути; `getEventPaths` может сканировать большой patch. Нужны ограничения входа с явным «покрытие неполное», не обещание нулевой задержки. Отдельный процесс тоже конкурирует за CPU и память.

**Опровергающий тест:** большой patch, поток nested events, два runtime, зависший дочерний процесс. Очередь ограничена, отменённый процесс не заменяется до подтверждённого завершения, доставка после teardown невозможна. Межпроцессный брокер отложить до измеренной проблемы дублирования.

### P1-K5 — Вопросы и тесты тоже требуют честного контракта

Сохраняю меньшинственный **P1-E** / **P1-H2** и **P3-H5**: выбранные пользователем обязательства полезны без детектора. Но отсутствие тестового свидетельства — не дефект; успешный тест и чтение агентом не доказывают отсутствие гонок или утечек.

Фильтр **P2-H9** «только attributed» теряет ценные shell/external изменения. Лучше показывать неизвестное авторство, чем подавлять риск. Автоматические чек-листы **P2-A5** не имеют нулевой стоимости: занимают контекст и меняют поведение.

Локальный subprocess не гарантирует отсутствие сети. Исполнение project config, передача кода модели и продолжение агента — разные разрешения.

**Опровергающий тест:** stale digest не отправляет вопрос; результат теста связан со снимком; неизвестный writer не маскируется; без согласия нет запуска, egress или продолжения.

Сохраняю **P1-H3**: workspace/worktree, снимок анализа и владелец доставки — разные идентичности.

Конвейер автоматической фазы:

Ошибка, пропуск, отмена, удаление объекта и подтверждённое исправление — разные состояния.

Для чтения нужны исключения generated/vendor/секретов, лимиты байтов/файлов, проверка выхода путей и symlink за разрешённую область. Durable baseline/suppressions — не scratch.

## Требуемые уточнения

### P1-S1 — Средняя важность: проверка всех входов пока является требованием, а не доступной возможностью

**Разделы 6, 7, 10:** формулировки «versions всех используемых inputs» и «проверить … все input versions» правильны как целевой контракт, но могут подразумевать отсутствующий интерфейс анализатора.

Проверенный `external/pi-tools-suite/src/lsp/shared-manager.ts:69–75` возвращает строку. В **P1-F3**, **P1-K3**, **P1-R3** не установлено, что существующий LSP/AST executable раскрывает полный набор прочитанных файлов, конфигурацию и версии документов.

**Исправление:** добавить capability-границу: строгий версионированный результат возможен только при известном наборе входов либо анализе контролируемого снимка. Иначе результат остаётся диагностикой производителя с явно ограниченной гарантией свежести; нельзя маркировать его как полностью перепроверенный межфайловый finding.

**Проверка:** анализатор читает скрытую зависимость, которая меняется при неизменном target. Система не должна обещать более сильную актуальность, чем способен подтвердить адаптер.

### P1-S2 — Средняя важность: разделить допустимость вычисления и публикации

**Раздел 6:** таблица разрешает fast tier по debounce, тогда как основной текст связывает automatic summary с успешным settlement. Из текста не вполне ясно, допускается ли анализ во время работающего агента и что происходит после failed/aborted settlement.

Это открытый выбор расписания, а не установленный консенсус: **P1-H5**, **P1-R1**, **P2-A10**, **P3-R1** различали режимы.

**Исправление:** явно назвать:
- условия постановки вычисления;
- условия публикации;
- поведение накопленных кандидатов после ошибки;
- допускается ли speculative fast tier вообще в первой автоматической фазе.

Для выбранного небольшого MVP достаточно оставить debounce объединением кандидатов, а вычисление запускать вручную или по успешному settlement. Более раннее вычисление — отдельная опция, не скрытое обязательство.

### P1-S3 — Средняя важность: абсолютная дедупликация с LSP недоказуема текущим интерфейсом

**Разделы 6 и 10:** «Не дублировать LSP findings» / «No duplicate diagnostics» выглядят абсолютным acceptance invariant.

**P1-F3**, **P1-H1**, **P1-K1** поддерживают устранение повторов, но строковый вывод без общей идентичности не позволяет гарантировать семантическую дедупликацию всех производителей.

**Исправление:** сузить критерий до проверяемого: не повторять диагностику, уже полученную через тот же адаптер/идентичность; пересекающиеся независимые результаты показывать с происхождением, не считать автоматически разными дефектами. Полноту межинструментальной дедупликации оставить ограничением, а не обещанием.

### P1-S4 — Низкая важность: привязать валидацию к фазам

**Раздел 10:** список полезен, но заголовок «обязательные будущие тесты» может сделать ручной MVP зависимым от реализации watcher, nested collector и reconciliation, которые исключены разделами 4 и 8.

**Исправление:** пометить проверки как:
- ручной MVP;
- событийная автоматизация;
- будущие graph/reconciliation/shared-runtime возможности.

Проверка отсутствия незапрошенного Git/execution нужна сразу; успешное обнаружение shell re-edit — только после появления соответствующего механизма. Это сохраняет небольшой эксперимент из **P1-R1**, не ослабляя будущие инварианты **P1-R3**.
